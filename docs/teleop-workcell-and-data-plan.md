## 1. 요약

- 수집 파이프라인(팔 3자유도 pick-place + 손 17관절, LeRobot 형식, `record_pick.sh`)은 실물에서 동작한다. 팔 추종 오차 평균 0.4 cm, 안전장치 작동 0회.
- **하드웨어 병목**:
  1. 노트북 포트 하나에 버스 전원 허브로 카메라 2대·CAN·손이 몰려 있다. CAN 어댑터 반복 끊김과 Orbbec 리셋이 여기서 나온다.
  2. CAN이 끊기면 팔이 힘이 빠져 쓰러진다.
  3. Orca 손의 반응이 느리고(333 ms) 캘리브레이션이 틀어진다.
- **데이터 품질 병목**: 웹캠 한 대 손 추적은 가려짐과 정면 기울기 인식 한계로 손가락·손목 값이 튄다. 모방학습/VLA는 시연이 일관될수록 잘 배우므로 입력 장치가 곧 데이터 품질이다.
- **추론**: 학습한 정책이 텔레오퍼레이션 자리에 들어가 카메라 영상 + 관절 상태로 관절 명령을 낸다. 카메라·트레이·조명·로봇 설정은 수집 때와 같아야 한다.
- **확장(제조 조립)**: 긴 공정을 정책 하나로 학습하기보다 스킬 단위로 나누고 상위에서 순서를 관리하는 계층형이 현실적이다.

## 2. 현재 시스템

### 2.1 하드웨어

| 장치 | 연결 | 역할 |
| --- | --- | --- |
| AgileX Nero 7축 팔 | candleLight CAN 어댑터(USB) → `can0` 1 Mbit/s. 웹 컨트롤러 192.168.0.150 | 팔 |
| Orca 손 (오른손, Feetech 17모터, 힘줄 구동) | CH343 USB 시리얼 `/dev/ttyACM0` | 손 |
| Orbbec Gemini 335 `CP0H953001AR` | USB (연장선 사용 중, USB 2.0으로 연결됨) | 관찰(데이터) 카메라 `observation.images.data` |
| Orbbec Gemini 335 `CP0H95300129` | USB 3 | 손 추적(색상+깊이) |
| Dell 노트북, Ubuntu 24.04, Intel Iris Xe | USB-C 포트 1개 → 버스 전원 허브 2단 | 녹화·텔레오퍼레이션 |

### 2.2 소프트웨어와 제어 흐름

```
손 추적 카메라 ─ MediaPipe(손 21점) ─┬─ retargeter → Orca 손가락 17관절 명령
                                     └─ 손바닥 3D 위치(깊이) + 손 기울기
                                          → arm_ik (pick-place 3자유도 IK) → Nero 관절 명령
                                          → Orca 손목 명령
녹화: 데이터 카메라 영상 + 관절 상태 24 + action 24 → LeRobot 데이터셋 (15 fps)
```

- 실행: `nero_orca/record_pick.sh` (실행법은 [native-linux-recording-setup.md](native-linux-recording-setup.md) §10).
- pick-place 모드: J3/J5/J6 고정, J7은 손 기울기(손끝 45° 아래) 유지, 손 위치는 J1/J2/J4. 시작 자세는 로봇 앞 52 cm, 손바닥 높이 23 cm. 범위는 앞뒤 ±10, 좌우 ±25, 아래 −9 / 위 +11 cm.
- Orca 손목: 사람 손 기울기를 따라감 (−40 ~ +25°, 숙이면 팔 아래 한계를 올려 책상 2 cm 여유 유지).

### 2.3 데이터 형식

| 키 | 차원 | 내용 |
| --- | --- | --- |
| `observation.state` | 24 | Nero 관절 7 + Orca 17 (손목 + 손가락 16), 도. 하드웨어 센서값 |
| `action` | 24 | 같은 순서의 명령값, 도 |
| `observation.images.data` | 480×640×3 | 데이터 카메라 |
| `observation.images.frontal` | 240×320×3 | MuJoCo 렌더. 실물 학습에는 빼는 것을 권장 (§7.3) |

## 3. 하드웨어 제약

### 3.1 아직 남아 있는 하드웨어 문제

| # | 문제 | 증상 | 영향 | 대책 |
| --- | --- | --- | --- | --- |
| H1 | **USB 전원·허브 구성** | 노트북 포트 하나에 버스 전원 허브 2단. 카메라 2대·CAN·손이 함께 물림 | H2, H3의 근본 원인으로 추정 | **셀프 파워드(전원 어댑터 있는) 허브**. CAN은 카메라와 다른 허브/포트로 분리. 짧고 좋은 케이블 |
| H2 | **CAN 어댑터 반복 끊김** | 이날 6회 이상 USB 연결 해제. 녹화 중 `failed to xmit URB: -EPIPE` 후 끊김 → 피드백 끊김 안전장치로 팔 정지 | 에피소드 뒷부분 무효, 팔 쓰러짐 위험(H4) | H1 해결. 포트 `3-3.1.3.1`에서 반복, `3-3.1.3.4`로 옮긴 뒤 안정. 재연결 시 `can0` 재활성화 + External CAN Push |
| H3 | **Orbbec 깊이+색상 리셋** | 레이저 5~6단계에서 0.1초 만에 카메라가 USB에서 빠짐 | 깊이 모드 사용 불가 | 레이저 3단계로 우회 중. H1 해결 후 재확인. Quest로 바꾸면 이 카메라가 필요 없음 |
| H4 | **CAN이 끊기면 팔이 쓰러짐** | enable 상태에서 CAN 선을 뽑자 토크가 빠져 쓰러짐 | 손·팔 파손, 부상 위험 | 선 작업 전 팔을 받치고 웹에서 disable. 케이블 고정(§5.5). H2 해결 |
| H5 | **Orca 손 반응 지연** | 명령 대비 약 333 ms 지연 (팔 133 ms) | 빠른 쥐기 동작에서 명령과 실제 차이 (상위 5% 18.8°) | 시연을 천천히. 장기: 제어 파라미터 조정 |
| H6 | **Orca 엄지 MCP 범위 부족** | 명령 −60~90°에 실제 −45~62° | 엄지 대립 동작 제한 | 기구·토크 한계로 추정. 제조사 확인 |
| H7 | **Orca 캘리브레이션 틀어짐** | 10/12 → 10/14 사이 모터 위치가 범위를 벗어남 | 손 값이 한계로 잘림 | 수집 세션마다 손 상태 점검, 필요 시 재캘리브레이션 (힘줄 늘어남 의심) |
| H8 | **Nero 속도·하중** | 속도 10%에서 명령 못 따라감. 손 무게 약 1.8 kg(모델 추정), 관절 부하 최대 76% | 추종 오차, 팔을 멀리 뻗는 자세 위험 | 속도 20% + 명령 0.4 rad/s 제한(해결). 손 무게 실측 |
| H9 | **노트북** | 남는 USB 포트 없음, 내장 GPU, 손 추적이 CPU 사용 | H1과 직결. 학습 불가 | 허브 교체. 학습은 GPU 서버. Quest로 손 추적 부하 제거 |

### 3.2 하드웨어처럼 보였지만 설정·소프트웨어 문제였던 것 (해결됨)

## 4. 텔레오퍼레이션 입력 장치

### 4.1 웹캠(현재)의 한계

- **가려짐**: 카메라 한 대라 손을 숙이거나 쥐면 손가락이 손바닥·손등 뒤로 가려지고, MediaPipe가 추측한 값이 튄다.
- **정면 기울기**: 카메라를 마주 본 상태에서 손목을 숙이는 동작은 깊이 방향 변화라 각도 인식이 부정확하다.
- **배치 딜레마**: 카메라를 손 아래에서 올려다보게 하면 손바닥은 보이지만 불편하다. 작업자 뒤에서 찍으면 손등만 보여 가려짐이 더 심하다.
- 결과적으로 같은 동작도 시연마다 action이 달라져 학습 데이터가 지저분해진다.

### 4.2 입력 방식 비교

| 방식 | 팔 | 손 | 정밀도 | 비용·복잡도 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 웹캠 + 깊이 (현재) | 위치 3자유도 | MediaPipe 21점 | 낮음 | 낮음 | 가려짐, 기울기 인식 한계 |
| **Meta Quest 3 손 추적** | 손목 6자유도 | 26관절 | 중간 | 낮음 | 다중 카메라라 가려짐에 강함. `orca_teleop --source metaquest` 일부 구현됨 |
| Quest 3 + Vive tracker | 손목 6자유도 (정밀) | Quest | 중상 | 중간 | 베이스 스테이션, SteamVR(Linux 까다로움), 두 좌표계 정합 필요 |
| Vive tracker + 데이터 장갑(Manus 등) | 손목 6자유도 | 장갑 센서 | 높음 | 높음 | 정밀 손 조작 연구의 표준 조합. `orca_teleop --source manus` 있음 |
| 리더–팔로워 팔 + 장갑/외골격 | 관절 그대로 | 장갑/외골격 | 가장 높음 | 높음 | IK 불필요. Nero 웹에 Linkage(leader/follower) 메뉴 있음 (리더 장비 여부는 AgileX 확인 필요). GELLO처럼 자작 가능 |

### 4.3 Quest 3로 시작할 때

- **사라지는 문제**: 손 추적 Orbbec이 빠져 허브 부하와 레이저 전력(H3)이 줄고, 손 추적 CPU 부하(H9)도 헤드셋으로 넘어간다.
- **필요한 것**
  - WebXR은 보안 연결(HTTPS 또는 localhost)이 필요하다. `ngrok`은 손 데이터가 외부 서버를 거치고 지연이 생기므로 쓰지 않는다. **`adb reverse tcp:8765 tcp:8765`** 를 쓰되, 노트북 포트가 없으므로 **무선 adb**로 연결한다.
  - 노트북과 Quest를 같은 공유기에 연결 (지연 최소화).
- **코드 작업**
  1. Quest의 손목 위치(미터, 공간 좌표)를 pick-place 팔 목표로 연결한다. 지금 `combined_sink`는 Quest 입력에서 팔을 움직이지 않는다.
  2. 손목 숙임은 Quest 손목 방향을 쓴다. `orca_teleop`의 `WristAngleEstimator`(기준 시점 대비 기울기)와 같은 방식이다.
  3. 범위·책상 안전장치·클러치(손을 놓으면 정지)는 그대로 쓴다.
- Vive tracker는 Quest 단독으로 손목 위치가 떨리거나 자주 끊길 때 추가한다.

## 5. 작업대 구성 (최종 권장)

### 5.1 배치도

```
                 [데이터 카메라: 로봇 뒤쪽 위, 약 45° 내려다봄]
                              │
        ┌─────────────────────┼──────────────────────┐
        │  작업대 (로봇 받침과 같은 면)                    │
        │                                              │
        │   [Nero 받침]──팔──▶  작업 영역 (로봇 앞 42~62 cm, │
        │                       좌우 ±25 cm)              │
        │                       ┌─────┐   ○ 테이프 시작 위치 │
        │                       │트레이│   (표시 5곳)       │
        │                       └─────┘                  │
        └──────────────────────────────────────────────┘
                 작업자 (Quest 3 착용, 로봇 옆 또는 뒤에서 같은 방향을 봄)
```

### 5.2 로봇과 작업 영역

- 작업대는 로봇 받침과 같은 높이(현재 설정의 책상 = 높이 0 기준). 높이가 다르면 pick-place 아래 한계를 다시 계산해야 한다.
- 물체와 트레이는 pick-place 범위 안에 둔다: 로봇 받침 중심에서 **앞으로 42~62 cm, 좌우 ±25 cm**. 손바닥 중심은 높이 14~34 cm 사이에서 움직인다.
- 트레이 바닥이 작업대 면보다 낮으면(서랍형) 손이 바닥까지 닿지 못한다. 높이를 재서 아래 한계에 반영한다.
- 트레이 위치와 물체 시작 위치(예: 5곳)를 **작업대에 테이프로 표시**한다.
- 팔을 멀리 뻗는 영역(60 cm 이상)은 관절 부하가 크므로 자주 쓰는 위치를 가운데(약 52 cm)에 둔다.

### 5.3 카메라

| 카메라 | 위치 | 이유 |
| --- | --- | --- |
| **데이터(관찰) 카메라** | 로봇 뒤쪽 위에서 약 45° 내려다보는 고정 거치대. 트레이가 화면 가운데 | 작업 영역·물체·놓을 자리·로봇 손이 모두 보이고, 손이 위에서 내려오는 경로가 가려지지 않음. 수평 구도는 배경이 절반 이상이었고, 오른쪽으로 돌리면 작업자가 찍혔다 |
| **손목(손등) 카메라** (추가 권장) | Orca 손등이나 손목에 고정, 손가락과 물체를 향함 | 잡는 순간을 가까이서 보여줘 정밀도에 크게 기여. 학습·추론 모두에 쓰려면 수집 전에 달아야 함 |
| 손 추적 카메라 | Quest로 바꾸면 불필요. 웹캠을 계속 쓴다면 손 높이보다 낮게, 30~45° 올려다보게, 40~70 cm | 손바닥·손가락 안쪽이 보여야 굽힘 추정이 좋아짐 |

- 데이터 카메라 화면에 **작업자, 손 추적 장비, 움직이는 사물이 나오지 않게** 한다. 사람이 찍히면 정책이 사람 움직임을 단서로 배운다.
- 거치대를 단단히 조이고, **기준 화면 사진을 저장**한다. 세션 시작 때마다 비교한다.
- 데이터 카메라는 가능하면 USB 3로 연결한다 (지금은 연장선 때문에 USB 2.0).

### 5.4 작업자

- Quest를 쓰면 작업자가 **로봇 옆이나 뒤에서 로봇과 같은 방향을 보고** 조작하는 것이 자연스럽다 (좌우 반전 불필요, 패스스루로 실물 확인).
- 작업자는 데이터 카메라 시야 밖에 선다.
- 비상정지 버튼은 작업자 손 닿는 곳에 고정한다.

### 5.5 전원·케이블·안전

- 셀프 파워드 USB 허브를 쓰고, CAN 어댑터는 카메라와 다른 포트에 연결한다.
- CAN·USB 케이블은 장력이 걸리지 않게 고정한다 (케이블 타이, 스트레인 릴리프). 선 정리 중 CAN이 빠져 팔이 쓰러진 적이 있다 (H4).
- 선 작업, 손 교체, 캘리브레이션 전에는 팔을 받치거나 손을 작업대에 얹은 뒤 웹에서 disable한다.
- 조명은 일정하게 (창문 햇빛 변화 피하기), 배경은 단순하게 유지한다.

## 6. 데이터 수집

### 6.1 에피소드 수

- 단일 픽앤플레이스(테이프 → 트레이)는 **50 에피소드로 시작**한다. ACT·Diffusion Policy·SmolVLA 등의 단일 작업 예제가 보통 작업당 50개 안팎이다.
- 시작 위치가 하나면 20~30개로도 될 수 있고, 위치를 다양하게 하면 50~100개가 필요하다.
- 50개로 학습 → 실제 실행 → 실패 상황 위주로 30~50개 추가하는 식으로 늘린다.

### 6.2 수집 규칙

1. 시작 위치를 정해 고르게 돌린다 (예: 표시 5곳 × 10회).
2. 매번 같은 방식으로: 위에서 접근 → 내려가기 → 쥐기 → 들어 올리기 → 트레이 위 이동 → 놓기.
3. 에피소드는 10~20초. 놓고 손을 떼면 바로 종료.
4. 실패한 에피소드는 번호를 적어 두고 나중에 지운다 (지금은 버리는 키가 없음).
5. 카메라·조명·트레이·배경·로봇 설정(pick-place, 속도 20%, 캘리브레이션)을 수집 내내 바꾸지 않는다.
6. 손 추적이 불안정한 자세(웹캠에서 손을 숙여 가려지는 동작)는 피하거나, Quest로 바꾼 뒤 모은다.

### 6.3 실행과 키

```bash
cd ~/workspace/nero_orca
NAME=pick-yellow-tape TASK="pick up the yellow tape and place it in the tray" EPISODES=50 ./record_pick.sh
# 두 번째 세션부터 이어 붙이기
KEEP=1 NAME=pick-yellow-tape TASK="pick up the yellow tape and place it in the tray" EPISODES=20 ./record_pick.sh
```

- 키는 **녹화 터미널을 클릭한 뒤** 누른다. 스페이스바: 저장 후 다음 에피소드, `q`: 저장 후 종료. 웹캠 창에서 `q`를 누르면 손 추적만 꺼지고 저장되지 않는다.
- 에피소드 사이: 팔·손이 시작 자세로 복귀 → `REST`초(기본 15) 동안 정지 → 이때 물체를 다음 위치에 놓는다.
- 저장 위치 `datasets/<NAME>/`, 로그 `datasets/<NAME>.log`.

### 6.4 데이터 수집 중 겪은 문제

| 문제 | 결과 | 예방 |
| --- | --- | --- |
| 저장 전에 녹화가 끝남 | `pick-yellow-tape`: 37초 녹화가 임시 PNG(299 MB)만 남고 영상·관절 데이터 없음 | 터미널에서 스페이스바/`q`로 끝내기. 이제 로그가 데이터셋별로 남는다 |
| CAN 끊김 | 에피소드 뒷부분 상태값 정지 | H1/H2 해결. 수집 후 상태값이 끝까지 변하는지 점검 |
| 손 방향 반대였던 시기의 데이터 | 손 관절값이 실제와 반대 | 2026-10-14 16:38 이전 데이터는 학습에 쓰지 않는다 (`orca-real-test`, 초기 `nero-orca-pick-real-test`, shadow 테스트들) |
| 웹캠 손 추적 잡음 | 손가락·손목 action이 튐 | Quest로 전환 |
| `frontal` 영상 | MuJoCo 렌더가 함께 저장됨 | 학습 설정에서 제외 |
| 녹화 15 fps | 빠른 접촉 순간이 성기게 기록됨 | 장기: 30 fps |

### 6.5 수집 후 점검 항목

- 프레임 수 ≈ 시간 × 15, 안전장치(`command held`) 로그 없음.
- 팔: 명령과 상태 차이 평균 < 1°.
- 손: 주먹 쥐는 구간에서 손가락 상태값이 크게 변하는지.
- 영상: 첫·중간·마지막 프레임에 작업 영역이 보이고 작업자가 없는지.

## 7. 학습과 추론

### 7.1 추론 때의 동작

학습한 정책이 텔레오퍼레이션 장치 자리에 들어간다.

```
매 주기(15 Hz): 데이터 카메라 영상 + 관절 상태 24 (+ VLA라면 작업 문구)
               → 정책 → action 24 (보통 수십 스텝을 한 번에 예측)
               → Nero 관절 명령, Orca 손가락·손목 명령
```

- action이 관절 각도이므로 추론 때는 IK·손 추적 없이 관절 명령을 바로 보낸다.

### 7.2 수집 때와 같아야 하는 것

| 항목 | 이유 |
| --- | --- |
| 카메라 위치·각도·해상도 | 정책은 화면 속 픽셀 위치로 물체와 손 위치를 판단한다. 몇 cm만 움직여도 성공률이 떨어진다 |
| 트레이 위치 | 놓을 위치를 화면 위치로 학습한다 |
| 조명·배경 | 영상이 달라 보이면 혼란 |
| 로봇 설정 | pick-place 모드, 손 캘리브레이션, 속도. action의 의미가 같아야 한다 |
| 물체 시작 위치 범위 | 학습 데이터 범위 안에서만 일반화된다 |

### 7.3 준비할 것

- **학습 환경**: GPU 서버 또는 클라우드 (노트북 내장 GPU로는 어려움). 데이터셋을 옮겨 LeRobot으로 학습 (단일 작업이면 ACT부터).
- **학습 입력**: `observation.images.data` (+ 손목 카메라), `observation.state`. `observation.images.frontal`은 제외.
- **추론 실행 프로그램 (아직 없음)**: 정책 로드 → 15 Hz로 카메라·상태 읽기 → 관절 명령 전송. 녹화와 같은 안전장치 필요:
  - 관절 속도 제한 (0.4 rad/s), 추종 오차·피드백 끊김 감시 (`hardware.py`)
  - **책상 높이 확인**: 명령 관절값으로 손 위치를 계산(MuJoCo)해 책상에 너무 가까우면 막기
  - pick-place 관절 관계 (J3/J5/J6 = 0, J7 범위) 확인
  - `combined_sink.py`의 하드웨어 연결과 안전장치를 재사용

## 8. 확장: 제조 조립 같은 긴 공정

### 8.1 두 가지 구성

| 방식 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| 긴 시퀀스 하나 | 조립 전체를 한 에피소드로 녹화, 정책 하나가 끝까지 수행 | 단순, 단계 전환도 학습 | 오차 누적(단계별 성공률의 곱: 95% × 10단계 ≈ 60%), 현재 단계 혼동, 데이터 많이 필요, 일부만 바꿔도 전체 재수집 |
| **스킬 분해 + 상위 순서 관리** | "모듈 A 집기", "지그에 끼우기", "체결"처럼 짧은 스킬로 나눠 학습. 위에서 순서 관리 | 스킬별 개선·재사용, 실패 지점 파악 쉬움 | 스킬 종료·성공 판단 필요 |

- 스킬 구현: 스킬마다 별도 정책, 또는 **언어 지시를 받는 VLA 하나에 단계별 문구**를 바꿔 넣기.
- 상위 순서 관리:
  - **상태 기계(스크립트)**: 정해진 순서 + 단계별 성공 확인. 순서가 고정된 제조 공정에 가장 적합하고 검증이 쉽다.
  - 고수준 모델(LLM/VLM 플래너): 장면을 보고 다음 스킬 선택. 유연하지만 예측 가능성이 낮다 (pi0.5, Hi Robot 계열).
- 스킬 종료·성공 판단: 정책의 "완료" 출력, 비전 성공 판별기, 힘·위치 센서. 실패 시 재시도/복구 스킬.

### 8.2 데이터

- 스킬 단위로 따로 녹화 (가장 쉬움, 작업 문구 = 스킬 이름), 또는 전체를 녹화하고 구간별로 단계 문구를 라벨링.
- 어긋난 상태에서 다시 맞추는 **복구 시연**을 일부러 포함하면 오차 누적에 강해진다.

### 8.3 제조 현장에서의 현실

- 이송·운반처럼 정해진 동작은 기존 방식(프로그래밍 경로, 지그, 비전 측위)이 빠르고 확실하다.
- 학습 정책은 위치가 매번 다르거나 접촉이 많은 단계(케이블 삽입, 유연 부품, 섬세한 끼우기)에 쓰는 혼합형이 많다.
- 요구 성공률(99% 이상), 사이클 타임, 안전 인증 때문에 힘 제어, 성공 확인, 실패 시 복구·정지 로직을 반드시 함께 둔다.

| 상황 | 권장 |
| --- | --- |
| 단계 2~3개, 연구·데모 | 긴 시퀀스 하나 |
| 순서 고정 제조 조립 | **스킬 분해 + 상태 기계** |
| 제품·순서가 자주 바뀜 | 스킬 + VLA 언어 지시 + 플래너 |

노란 테이프 픽앤플레이스는 이 구조의 **스킬 하나**다.
